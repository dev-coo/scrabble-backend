# 협업 가이드 (사람용)

> 작성일: 2026-07-19

이 문서는 **팀원(사람)이 읽는 진행 안내서**입니다.
Claude의 코드 작업 규칙은 각 저장소의 `CLAUDE.md`에 따로 있습니다.

---

## 1. 역할

| 사람 | 역할 |
|------|------|
| **a** | 프론트 / 백 개발 (로테이션) |
| **b** | 프론트 / 백 개발 (로테이션, a와 반대편) |
| **c** | 깍뚜기 — 프론트·백 양쪽에 유동적으로 합류 |
| **d** | 총괄 · 멘토 (진행 관리, 리뷰, API 계약 조율) |

## 2. 로테이션 (예시)

한 사람이 프론트·백을 번갈아 맡아 **양쪽 티어를 모두 경험**하는 것이 목표입니다.

| 페이지 | 프론트 | 백엔드 |
|--------|--------|--------|
| 대기실 | a | b |
| 플레이 | b | a |

- **c**는 그때그때 손이 필요한 쪽에 합류합니다.
- **d**는 로테이션·리뷰·API 계약 합의를 총괄합니다.

## 3. "기능 단위"란

한 번의 요청 = 기능 하나. 페이지 전체는 기능 단위가 **아닙니다.**

- ✅ 좋은 단위: "방 목록 UI", "방 생성 API(`POST /rooms`)", "닉네임 입력 필드"
- ❌ 너무 넓음: "대기실 페이지 만들어줘", "백엔드 다 만들어줘"

넓게 요청하면 Claude가 거절합니다. 스스로 쪼개 오거나, 정 모르겠으면 Claude에게 **"추천해줘"**라고 하세요.

## 4. 프론트 ↔ 백 API 계약 합의 절차

프론트와 백은 **API라는 약속(계약)**으로만 연결됩니다. 코드보다 계약을 먼저 맞춥니다.

1. 기능을 시작하기 전에 **프론트·백 담당이 API 계약을 함께 정합니다.**
   - 엔드포인트 (예: `POST /rooms`)
   - 요청 형식 (보내는 JSON)
   - 응답 형식 (받는 JSON)
   - 에러 형식
2. 각 저장소의 `docs/api-contract.md`에 **같은 내용**을 기록합니다.
3. **d(멘토)가 양쪽 계약이 일치하는지 확인**합니다.
4. 합의 후 각자 독립적으로 개발합니다.
   - 프론트는 백이 늦으면 **목(mock) 데이터**로 먼저 진행할 수 있습니다.

## 5. 커밋 규칙

- **기능 하나 완성 = 커밋 하나** (약간 널널해도 됨).
- 커밋 메시지는 무엇을 했는지 알 수 있게. (예: `feat: 방 목록 UI 추가`)
- 커밋 전 **d의 리뷰**를 거칩니다.

## 6. 프롬프트 기록

- Claude에게 입력한 프롬프트는 `PROMPTS.md`에 자동 기록됩니다.
- 주기적으로 커밋/푸시해서 **서로 어떤 지시를 했는지 비교·회고**합니다.
